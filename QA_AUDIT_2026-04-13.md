**Data**: 13 Aprile 2026  
**Auditor**: Lead QA Engineer  
**Scope**: Analisi completa post-implementazione auth/sessione, RLS multi-tenant e Piano dei Conti  
**Build Status**: 🔴 **HIGH RISK - Multiple P0 blockers identified**

---

## Executive Summary

Audit condotto sulla build deployata dopo gli interventi su:
- Auth/sessione con `auth_user_id` link (migration `20260412113000`)
- RLS multi-tenant isolation (migration `20260412130000`)
- Fiscal societa scope (migration `20260412143000`)
- Piano dei Conti con scope
- Access scope columns

**Risultato**: Individuate **17 problematiche critiche** di cui **6 P0 blockers** che impediscono l'utilizzo normale dell'applicazione.

## 🔴 P0 - CRITICAL BLOCKERS (6)

### P0-01: Piano Conti queries falliscono per mancanza societa_id scope
**Area**: Piano dei Conti / RLS  
**Severity**: P0 (Blocker)  
**Impact**: Piano dei Conti completamente inaccessibile

**Step per riprodurre**:
1. Login con utente qualsiasi
2. Navigare a "Piano dei Conti"
3. La query SELECT fallisce con violazione RLS

**Comportamento atteso**:
Piano dei Conti carica i conti della società selezionata

**Comportamento reale**:
```
Error: RLS policy violation on piano_conti
Policy: societa_scoped_generic_policy_piano_conti requires societa_id
```

**Root cause**:
- Migration `20260412130000_rls_multi_tenant_isolation.sql` aggiunge colonna `societa_id` a `piano_conti` (riga 41)
- Crea policy RLS che richiede `user_has_societa_access(societa_id)` (riga 481-484)
- Query esistenti in `src/modules/piano_conti/index.jsx` non filtrano per `societa_id`
- Righe esistenti in DB hanno `societa_id = null`

**File coinvolti**:
- `src/modules/piano_conti/index.jsx` (tutte le query SELECT)
- `supabase/migrations/20260412130000_rls_multi_tenant_isolation.sql`
- Tabella `piano_conti` (data migration necessaria)

**Rischio regressione**: ALTO - Bloccante per qualsiasi operazione contabile

### P0-03: utenti_studio_societa richiede auth_user_id ma utenti legacy non linkati
**Area**: Auth / User Management  
**Severity**: P0 (Blocker)  
**Impact**: Utenti esistenti senza `auth_user_id` non possono accedere a nessuna società

**Step per riprodurre**:
1. Utente legacy (creato prima delle migration) effettua login
2. Backend recupera profilo ma `auth_user_id` è NULL
3. Query su `utenti_studio_societa` fallisce (constraint unique)
4. Utente vede schermata vuota / errori di permessi

**Comportamento atteso**:
Utenti legacy vengono linkati automaticamente o fallback funziona

**Comportamento reale**:
- Fallback in `lib/auth.js` (getAuthenticatedContext, riga 73-97) gestisce email match
- Ma la tabella `utenti_studio_societa` richiede `auth_user_id NOT NULL` (migration riga 4)
- Se l'utente legacy non ha società in `utenti_studio_societa`, resta fuori

**Root cause**:
- Migration `20260412130000` crea `utenti_studio_societa` con `auth_user_id NOT NULL`
- Non c'è script di backfill che popola la tabella per utenti legacy
- Utenti pre-esistenti non hanno mappatura società

**File coinvolti**:
- `lib/auth.js` (getAuthenticatedContext)
- `lib/authorization.js` (getAuthorizedSocietaIdsForUser)
- `supabase/migrations/20260412130000_rls_multi_tenant_isolation.sql`

**Rischio regressione**: CRITICO - Lock-out utenti produzione

### P0-04: Session profile timeout troppo aggressivo causa loop login
**Area**: Auth / Session  
**Severity**: P0 (Blocker)  
**Impact**: Login fallisce o richiede ripetuti tentativi

**Step per riprodurre**:
1. Backend API lento o cold start (primo avvio dopo deploy)
2. Login con credenziali valide
3. `fetchSessionProfile` timeout a 7000ms (`src/lib/auth.js` riga 64)
4. Fallback costruisce profilo da auth metadata
5. Ma profile manca `id` valido → queries falliscono
6. UI rimane in "Caricamento sessione..."

**Comportamento atteso**:
Login riesce anche con backend lento, con fallback funzionale

**Comportamento reale**:
- Timeout dopo 7s
- Fallback profile ha `id = user.id` (auth UUID), non `utenti_studio.id`
- Queries downstream cercano `utenti_studio.id` → 404/null
- User bloccato

**Root cause**:
- `src/lib/auth.js` riga 64: timeout 7000ms troppo basso per cold start
- `App.jsx` riga 262-266: watchdog 12000ms inconsistente
- Fallback profile (riga 46-57) usa `user.id` invece di cercare `utenti_studio.id`

**File coinvolti**:
- `src/lib/auth.js` (fetchSessionProfile)
- `src/App.jsx` (syncAuthenticatedUser, watchdog)
- `api/auth/session.js` (endpoint /api/auth/session)

**Rischio regressione**: ALTO - UX pessima, abbandono utenti

### P0-05: RLS policies su prima_nota_righe e partitario causano deadlock nested queries
**Area**: Contabilità / RLS  
**Severity**: P0 (Blocker)  
**Impact**: Salvataggio/lettura prima nota fallisce con timeout

**Step per riprodurre**:
1. Vai a "Prima Nota Guidata"
2. Crea nuova registrazione con più righe
3. Salva
4. Query INSERT su `prima_nota_righe` triggera policy RLS (riga 410-436)
5. Policy esegue subquery su `prima_nota` per verificare permessi
6. Nested query causa deadlock o timeout su transazioni complesse

**Comportamento atteso**:
Salvataggio prima nota con righe riesce in <500ms

**Comportamento reale**:
- Timeout dopo 30s+
- Errore: "could not serialize access due to concurrent update"
- Rollback transazione

**Root cause**:
- Policy `prima_nota_righe_policy` (migration riga 410-436) esegue `EXISTS (SELECT FROM prima_nota)`
- Policy `prima_nota_partitario_policy` (riga 438-464) stesso problema
- Queries annidate con JOIN + RLS causano deadlock in Postgres
- Trigger `trg_prima_nota_righe_scope_defaults` (riga 310-314) aggrava il problema

**File coinvolti**:
- `supabase/migrations/20260412130000_rls_multi_tenant_isolation.sql`
- `services/primaNotaService.js` (INSERT/UPDATE batch)
- `domain/primaNotaPipeline.js`

**Rischio regressione**: CRITICO - Core workflow bloccato

## Top 5 Root Cause Sistemiche

### 1. **RLS Migration senza Data Backfill** (Impatto: CRITICO)
Migration `20260412130000` aggiunge colonne `societa_id` a multiple tabelle e attiva RLS policies, ma:
- Non popola `societa_id` su righe esistenti (tutte NULL)
- Non crea script di backfill
- Policy RLS blocca accesso a dati legacy
- **Fix**: Backfill script + default triggers

### 2. **Frontend Queries non aggiornate per societa_id** (Impatto: ALTO)
Tutti i moduli React fanno query SELECT senza filtro `societa_id`:
- `piano_conti`, `causali_contabili`, `causali_iva`, `percipienti`
- `partitario`, `registri_iva`, `liquidazione_iva`
- **Fix**: Refactor sistematico query layer

### 3. **Nested RLS Policies causano deadlock** (Impatto: CRITICO)
Policy `prima_nota_righe` e `partitario` con `EXISTS (SELECT FROM prima_nota)`:
- Subquery RLS su parent table
- Deadlock in batch INSERT/UPDATE
- **Fix**: Policy redesign con materialized auth context

### 4. **utenti_studio_societa mapping incompleto** (Impatto: CRITICO)
Nuova tabella bridge richiede dati per ogni utente-società:
- Utenti legacy non mappati
- Nuovi utenti non ricevono società di default
- `auth_user_id NOT NULL` blocca fallback
- **Fix**: Migration di backfill + UI update

### 5. **Session timeout inconsistente** (Impatto: ALTO)
3 timeout diversi:
- `fetchSessionProfile`: 7000ms
- App watchdog: 12000ms
- Backend slow start: 15000ms+
- **Fix**: Timeout unificato 20000ms + retry logic
