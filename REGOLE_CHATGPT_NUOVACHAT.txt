CONTESTO OPERATIVO RIUTILIZZABILE — FiscoSim

Stiamo sviluppando FiscoSim, gestionale contabile/fiscale interno avanzato per studio commercialista.

FiscoSim non è un SaaS, non deve diventare un prodotto vendibile ad altri studi e non deve integrare direttamente invii Agenzia Entrate, SDI o conservazione. Deve invece diventare uno strumento interno molto veloce, moderno e affidabile per gestire:

L’obiettivo è superare la logica operativa di NES, mantenendo però la stessa velocità d’uso per l’operatore esperto.

1. Metodo di sviluppo obbligatorio
Regola base

Non bisogna fare implementazioni “a caso” o semplici contenitori di dati.
Ogni funzione va progettata prima dal punto di vista:

contabile
operativo
UX
tecnico
dati output
integrazione futura

Prima di implementare una funzione bisogna sempre chiedersi:

1. Qual è il lavoro reale dell’operatore?
2. Quali dati FiscoSim conosce già?
3. Quali dati deve davvero inserire l’operatore?
4. Cosa può essere calcolato automaticamente?
5. Cosa può essere corretto manualmente?
6. Quali controlli evitano errori?
7. Quale output dati serve ai moduli successivi?

Se queste risposte non sono chiare, prima si ragiona e solo dopo si scrive il prompt.

2. Regola sui report Codex

Quando viene incollato un report Codex, non bisogna dare subito il prompt successivo.

L’ordine corretto è:

1. Audit del report
2. Verifica file modificati
3. Controllo perimetro
4. Controllo regressioni
5. Controllo se sono stati creati file enormi
6. Controllo test/build
7. Indicazione dei test manuali necessari
8. Verdetto: ok / non ok / ok tecnico ma serve test browser
9. Solo dopo, se confermato, prompt successivo

Se emergono bug, si ferma la scaletta principale e si corregge prima il bug.

Se emerge una miglioria:

se è bloccante, si fa subito;
se è utile ma non bloccante, si mette in scaletta;
se è futura, si mette nel backlog.
3. Regola contro micro-prompt e micro-implementazioni

Non fare 10.000 prompt inutili.

La regola corretta è:

1 prompt = 1 blocco logico completo ma controllato

Si accorpano più interventi se:

riguardano lo stesso flusso;
toccano lo stesso perimetro;
hanno stesso obiettivo;
si possono testare insieme;
non aumentano troppo il rischio.

Si separano invece se:

serve migration DB delicata;
si toccano moduli diversi;
si passa da draft a persistenza reale;
si cambia contratto dati;
serve prima validare manualmente.
4. Regola file piccoli / no file enormi

Non accumulare tutto dentro una view enorme.

Regole:

- View principale = solo orchestrazione
- Business logic fuori JSX
- Funzioni pure in domain/application
- Componenti UI piccoli e dedicati
- Se una feature cresce, creare file dedicato
- Non fare “aggiungo qui e poi splittiamo dopo”

Quando possibile:

nuova funzione → file dedicato;
nuovo pannello → componente dedicato;
nuova normalizzazione → helper puro;
nuovo calcolo → funzione pura testabile.

Regola operativa fondamentale
La scrittura contabile può essere confermata solo con un SOTTOCONTO.
Mastro e Conto sono visibili/navigabili ma non registrabili.

Nelle causali contabili/template:

si può salvare un Sottoconto;

11. Registrazione manuale — principi operativi

La Registrazione manuale deve essere progettata come modulo veloce, non come form lento.

Flusso base
Nuova registrazione
→ data registrazione
→ causale contabile
→ dati documento se richiesti
→ soggetto se richiesto
→ righe PN precompilate
→ IVA se richiesta
→ partitario se richiesto
→ ritenute se richieste
→ F12 salva
Causale contabile

Il comportamento deve derivare dalle impostazioni della causale, non dal codice causale.

Campi causale usati:

tipo_causale
operazione_partite
gestione_partite
op_ritenute
tipo_documento
data_documento
numero_documento
flag IVA/CEE/differita

Il codice causale può essere solo fallback se mancano dati configurativi.

12. Righe Prima Nota — priorità

Le righe PN si generano con questa gerarchia:

1. Template righe salvato nella causale contabile
2. Storico struttura causale per società
3. Fallback behavior causale

Poi, dentro una riga generica, il conto specifico si risolve così:

1. conto preimpostato nell’anagrafica/piano dei conti della controparte
2. storico registrazioni per soggetto/causale/ruolo
3. conto generico da future impostazioni procedure collegate alla causale
4. manuale / da scegliere
Importante

Lo storico struttura causale non è lo storico del singolo fornitore.

Risponde a:

Con questa causale, per questa società, quali righe si usano di solito?

Esempio:

Società SIRIA SRL
Causale FF
Pattern storico:
- Fornitore Avere
- IVA Dare
- Costo Dare

Lo storico soggetto invece risponde a:

Quale conto specifico uso per questo fornitore/cliente?

17. Validazioni

Distinguere sempre:

blockers
warnings
info
Blockers

Solo ciò che impedisce registrazione contabile corretta:

PN non quadrata;
riga senza sottoconto finale;
importi negativi gravi;
causale obbligatoria mancante;
soggetto mancante se partitario obbligatorio.
Warnings

Problemi da correggere ma non sempre bloccanti:

IVA incompleta;
registro IVA mancante;
residuo IVA diverso da zero;
partitario predisposto ma non reale;
ritenute incomplete.
Info

Elementi solo informativi:

CU/770 non ancora generati;
partitario non ancora chiuso realmente.
