## 10. Raccomandazioni operative

### Cosa fare:
1. **Procedere per blocchi piccoli**: un problema alla volta, come previsto da REGOLE_CODEX
2. **Testare dopo ogni modifica**: `npm run build` + test automatici esistenti
3. **Backup frequenti**: ZIP settimanali del progetto
4. **Commit piccoli e focalizzati**: una funzionalità per commit
5. **Usare Cline per**: audit architetturali, refactoring mirati, analisi dominio contabile
6. **Usare Copilot per**: completamento codice routine, boilerplate

### Cosa evitare:
1. **Refactor enormi**: non rifare da zero funzioni funzionanti
2. **Modifiche trasversali**: un file alla volta
3. **Scelte arbitrarie**: su conti, causali, soggetti senza configurazione
4. **Toccare legacy**: non modificare `prima_nota_guidata.jsx`, `import_fatture/`, `import_unificato/`
5. **Modificare DB senza approval**: no migration senza conferma esplicita

### Quando usare modelli diversi:
- **Cline (io)**: audit, architettura, dominio contabile complesso, refactoring strategico
- **Copilot**: completamento codice, fix sintattici, boilerplate
- **Modelli più potenti (GPT-4, Claude Opus)**: quando serve ragionamento fiscale molto complesso o analisi di grandi codebase

### Quando fare commit/backup:
- **Commit**: dopo ogni microfix testato, massimo 2-3 file modificati
- **Backup ZIP**: prima di interventi importanti, ogni 2-3 giorni di lavoro intenso
- **Checkpoint git**: alla fine di ogni blocco funzionale completato
